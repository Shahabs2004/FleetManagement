# مشخصات جامع پروژه: سامانه مدیریت ناوگان حمل‌ونقل (FleetManagement)

> این سند نتیجه‌گیری نهایی تمام تصمیم‌های اتخاذشده در محاوره است. هرجا دو تصمیم متعارض بوده، **آخرین تصمیم** ملاک است (بخش ۲۰ فهرست این اصلاحات را دارد). تمام کد، کلاس‌ها، متدها و قواعد مهم باید **کامنت فارسی** داشته باشند.

---

## ۱. نقش و روش کار

تو یک معمار نرم‌افزار و توسعه‌دهنده ارشد .NET هستی. پروژه را مرحله‌به‌مرحله بساز، هر مرحله را Build و Test کن و در مخزن GitHub ذخیره کن:
`https://github.com/Shahabs2004/FleetManagement` (عمومی؛ شاخه‌های `main` پایدار، `develop` توسعه، `feature/*` قابلیت‌ها).

قواعد کار:
- هیچ رمز، اطلاعات اتصال یا داده واقعی سازمان وارد مخزن نشود.
- هر چیزی را «انجام‌شده/آزمایش‌شده» اعلام نکن مگر با شواهد (نتیجه CI / تست).
- تا پایان کار ادامه بده؛ اگر روند متوقف شده، وضعیت مخزن و CI را بررسی و از همان نقطه ادامه بده.
- فایل‌ها و کلاس‌ها **کوچک و تک‌مسئولیتی** باشند؛ نام‌گذاری فنی انگلیسی (استاندارد C#)، کامنت و مستندات فارسی.
- UI، پیام‌ها، خطاها و مستندات برای کاربر: فارسی.

## ۲. فناوری و معماری

- .NET 10 LTS، C# 14، ASP.NET Core 10، **Blazor Web App – Interactive Server**، SignalR
- Entity Framework Core 10 + Migrations (SQL دست‌نویس فقط در بخش‌های سنگین/ضروری)
- SQL Server موجود سازمان، **اتصال با SQL Authentication** (یک حساب SQL برای ساخت/به‌روزرسانی جداول و اجرای روزمره)
- میزبانی: یک Windows Server + IIS؛ قابلیت انتقال بعدی برنامه به سرور جدا
- **Clean Architecture به‌صورت Modular Monolith**: لایه‌های Presentation / Application / Domain / Infrastructure؛ ماژول‌ها: کاربران و دسترسی، رانندگان، خودروها، مأموریت‌ها، درخواست‌ها، تایم‌لاین، گزارش‌ها و داشبورد، اعلان‌ها، پیامک، تنظیمات و راه‌اندازی، ممیزی و سوابق نشست. هر ماژول سرویس، اعتبارسنجی و منطق کسب‌وکار خودش را دارد و ارتباط ماژول‌ها از طریق قراردادها (Interfaces) است.
- مرورگرها: Edge، Chrome، Firefox (نسخه‌های به‌روز). فقط دسکتاپ/لپ‌تاپ؛ بدون طراحی موبایل/تبلت.
- ظرفیت: ۲۰ تا ۵۰ کاربر هم‌زمان، حداکثر ۲۰ راننده و ۲۰ خودرو؛ ساختار قابل توسعه.
- عملکرد: بارگذاری مرحله‌ای، جست‌وجو/فیلتر سمت سرور، دریافت حداقل داده برای هر صفحه، به‌روزرسانی زنده تغییرات مهم با SignalR (هماهنگ با همان زیرساخت Blazor Server، بدون ارتباطات مستقل اضافی؛ پس از قطع ارتباط، همگام‌سازی مجدد).
- ذخیره زمان‌ها در پایگاه داده به‌صورت استاندارد (UTC/میلادی)، نمایش شمسی با Asia/Tehran. پردازش و ذخیره اعداد انگلیسی/استاندارد، **نمایش تمام اعداد فارسی**.

## ۳. زیرساخت، راه‌اندازی اولیه و بازیابی

1. **راه‌اندازی خودکار**: اولین اجرا روی IIS، وضعیت را تشخیص می‌دهد و ویزارد `/setup` را نشان می‌دهد؛ بعد از تکمیل، ویزارد برای همیشه قفل می‌شود. ری‌استارت IIS یا اجرای مجدد، داده/تنظیمات را حذف نمی‌کند.
2. **ایجاد Administrator محلی** (مستقل از AD) با **کد یک‌بارمصرف** (اعتبار ۲۴ ساعت) که روی سرور تولید و در فایل محافظت‌شده قرار می‌گیرد. نام کاربری/رمز را خود مدیر تعیین می‌کند؛ هیچ رمز پیش‌فرض در کد نیست. رمز با PBKDF2 هش می‌شود. اگر راه‌اندازی نیمه‌تمام ماند، قابل ادامه است.
3. مراحل ویزارد: (الف) اتصال SQL (آدرس/Instance، نام DB، کاربر/رمز) + آزمایش اتصال + ایجاد خودکار DB و جداول با Migration؛ (ب) تنظیم Active Directory (آدرس، دامنه، LDAPS، گروه‌های مجاز، نگاشت گروه→نقش، آزمایش اتصال)؛ (پ) تنظیم پیامک ADP (فقط با **کد دسترسی جداگانه مدیر فنی** که روی سرور تولید و هش آن نگهداری می‌شود؛ حتی رد کردن این مرحله هم نیازمند آن است)؛ (ت) نام و لوگوی سازمان، واحدهای سازمانی، نقش‌ها، تنظیمات مأموریت؛ (ث) **آزمون جامع آمادگی** (SQL، AD، گروه‌ها، پیامک، تنظیمات سازمان) و بعد قفل ویزارد.
4. اگر پیامک در دسترس نباشد، بهره‌برداری مجاز است (پیامک‌ها در صف می‌مانند). اگر AD در راه‌اندازی در دسترس نباشد، راه‌اندازی با AD ناقص مجاز است (تنظیمات ذخیره می‌شود؛ فقط Administrator محلی وارد می‌شود تا AD برقرار شود).
5. **تنظیمات تماماً در SQL Server و بدون رمزنگاری** ذخیره می‌شوند (پذیرش آگاهانه ریسک، شبکه داخلی محافظت‌شده)؛ برای پشتیبان‌گیری/بازیابی ساده. **استثنای محدود**: اطلاعات حداقلی اتصال SQL (محافظت با DPAPI) و هش رمز Administrator در فایل محلی محافظت‌شده روی سرور (ACL فقط برای مدیران سرور، SYSTEM و هویت Application Pool؛ اسکریپت PowerShell برای تنظیم) تا ورود اضطراری هنگام قطع SQL ممکن باشد. این فایل هرگز وارد GitHub نشود.
6. **Administrator محلی** پس از راه‌اندازی هم فعال و مستقل از AD می‌ماند (دسترسی کامل، رمز قابل تغییر، ورودها ممیزی می‌شوند، از پنل عادی قابل حذف/غیرفعال‌سازی نیست).
7. **حالت بازیابی امن/اضطراری محدود**: هنگام قطع SQL فقط Administrator محلی وارد صفحه بازیابی زیرساخت (SQL، AD، پیامک) می‌شود؛ سایر بخش‌ها بسته‌اند؛ پس از وصل شدن SQL بازگشت به حالت عادی.
8. **به‌روزرسانی کنترل‌شده**: انتشار نسخه جدید روی IIS توسط مسئول فنی؛ بررسی سازگاری، اعمال Migration، ثبت نتیجه، جلوگیری از اجرای ناسازگار؛ بررسی وجود پشتیبان معتبر SQL پیش از Migration. پشتیبان‌گیری توسط خود SQL Server است و ماژول Backup در برنامه نیست.
9. خطاهای سامانه: پیام فارسی قابل فهم به کاربر + **شناسه پیگیری**؛ جزئیات فنی و اطلاعات حساس فقط در لاگ سرور؛ **هیچ اعلان مجزا** برای خطاهای فنی ارسال نمی‌شود.

## ۴. احراز هویت و دسترسی

- ورود: **Windows Integrated Authentication روش اصلی**؛ صفحه ورود با نام کاربری/رمز دامنه روش جایگزین (LDAPS ترجیحاً).
- ورود اولیه فقط برای اعضای گروه‌های مجاز AD؛ پروفایل در اولین ورود خودکار ساخته می‌شود. در **هر ورود** همگام‌سازی AD انجام می‌شود (فعال/قفل/منقضی بودن حساب، عضویت مستقیم و تودرتوی گروه‌ها، نام، واحد سازمانی).
- حساب غیرفعال/قفل/خارج از گروه مجاز یا غیرفعال‌شده داخل سامانه، وارد نمی‌شود. غیرفعال‌سازی داخلی با فعال شدن دوباره AD برداشته نمی‌شود (فقط مدیر سیستم).
- قطع AD: ورود جدید مسدود؛ نشست‌های فعال تا انقضا ادامه دارند؛ احراز هویت آفلاین وجود ندارد؛ پس از وصل، بررسی مجدد حساب و گروه‌ها.
- نشست: پیش‌فرض ۸ ساعت عمر مطلق و ۳۰ دقیقه عدم فعالیت؛ هر دو توسط مدیر سیستم قابل تنظیم.
- پروفایل کاربر: نام، نام خانوادگی، نام کاربری AD، واحد سازمانی (از AD و به‌روزرسانی خودکار؛ اصلاح دستی مدیر سیستم اولویت دارد تا زمان تغییر مجدد/همگام‌سازی دستی)، نقش‌ها. هر کاربر یک واحد سازمانی اصلی دارد. **گروه اداری** کاربر از گروه‌های AD (مثل اعتبارات، امور مشتریان، امور مالی، رایانه) استخراج می‌شود و مدیر سیستم می‌تواند برای هر گروه AD نقش/مجوز تعریف کند.
- نقش‌های پایه: **مدیر سیستم، مدیر ناوگان، اپراتور، مشاهده‌گر** + امکان نقش جدید و ویرایش مجوزهای هر نقش. چند نقش هم‌زمان برای یک کاربر (ترکیب مجوزها). مجوزها در سطح عملیات (مشاهده/افزودن/ویرایش/حذف‌یا‌بایگانی برای هر موجودیت).
- اولویت: **منع صریح (Explicit Deny) مدیر سیستم** > مجوز/تنظیم دستی مدیر سیستم > مجوزهای گروه AD. همه تغییرات نقش/مجوز ممیزی می‌شوند.
- مجوزهای مستقل و قابل اختصاص به نقش/کاربر: مشاهده گزارش ممیزی، مشاهده گزارش پیامک‌ها، مشاهده سوابق نشست/ورود، تمدید مأموریت، تقسیم مأموریت، بررسی/تأیید درخواست‌ها و تغییرات، ثبت/اصلاح کیلومتر و … 
- لیست کاربران: جست‌وجو فقط بر اساس نام و نام کاربری AD (بدون فیلتر پیشرفته).

## ۵. اطلاعات پایه

### رانندگان
- فیلدها دقیقاً: نام، نام خانوادگی، شماره موبایل، وضعیت همکاری (**فعال / مرخصی / خاتمه کار / غیرفعال**) + خودروی اختصاصی پیش‌فرض اختیاری (مدل ترکیبی: فقط پیش‌فرض است، نه اجباری؛ تخصیص واقعی در هر مأموریت مستقل ثبت می‌شود).
- فقط راننده «فعال» قابل تخصیص است. ویرایش موبایل: مدیر سیستم، مدیر ناوگان، اپراتور مجاز.
- حذف فیزیکی ممنوع برای رکورد دارای سابقه؛ **بایگانی/غیرفعال‌سازی** با حفظ سوابق؛ بازفعال‌سازی توسط مجاز با کنترل شرط (راننده باید «فعال» باشد). تاریخچه تمام تغییرات (قبل/بعد، کاربر، زمان).
- ثبت و ویرایش **فقط دستی** (بدون ورود گروهی Excel). فهرست با جست‌وجو و فیلتر.

### خودروها
- فیلدها: برند، مدل، **پلاک ملی ایران** (فرم استاندارد با فیلدهای جدا: عدد دو رقمی، حرف، عدد سه رقمی، کد دو رقمی ایران؛ اعتبارسنجی و پیش‌نمایش گرافیکی پلاک؛ ذخیره ساختاریافته برای جست‌وجو)، وضعیت.
- وضعیت‌ها: `ready` آماده‌به‌کار (دستی)، `mission` در مأموریت (**خودکار** از مأموریت فعال)، `repair` تعمیرگاه (دستی)، `out` خارج از سرویس (دستی).
- قواعد: تا وجود مأموریت فعال، تغییر به تعمیرگاه/خارج از سرویس ممنوع؛ وضعیت خودکار هرگز وضعیت دستی تعمیرگاه/خارج را بازنویسی نمی‌کند؛ پس از پایان مأموریت اگر وضعیت دستی تعمیرگاه/خارج بوده حفظ می‌شود و فقط در نبود مأموریت فعال و محدودیت دستی «آماده‌به‌کار» می‌شود. بایگانی/بازفعال‌سازی مثل راننده (خودرو نباید تعمیرگاه/خارج باشد). تاریخچه کامل تغییرات. فهرست با جست‌وجو/فیلتر.

### مکان‌ها
- فقط **نام** (یکتا). مبدأ/مقصد/توقف‌ها از فهرست انتخاب می‌شوند. همه کاربران می‌توانند مکان پیشنهاد دهند → «در انتظار تأیید» → فقط مدیر سیستم تأیید/رد/ویرایش/غیرفعال می‌کند. نام تکراری/مشابه: هشدار، ولی ارسال پیشنهاد مجاز. مکان‌های دارای سابقه حذف نمی‌شوند.

### واحدهای سازمانی
- فهرست ساده بدون سلسله‌مراتب؛ افزودن/ویرایش/غیرفعال‌سازی توسط مدیر سیستم.

## ۶. درخواست مأموریت

- هر کاربر واردشده می‌تواند درخواست ثبت کند. **فرم درخواست**: مقصد، تاریخ/بازه موردنظر، مبدأ، هدف/علت، نوع (حمل بار/مسافر)، تعداد همراهان/مسافران، توضیحات تکمیلی، نام درخواست‌کننده و واحد (خودکار)، **گروه درخواست‌کننده** (انتخاب یکی از گروه‌های AD خود کاربر)، **شماره موبایل** (وارد/تأیید در هر درخواست و ذخیره مستقل در پرونده مأموریت؛ تغییر پروفایل اثری ندارد). راننده/خودرو در درخواست انتخاب نمی‌شود.
- **انتخاب بازه روی تایم‌لاین عمومی** (بدون نمایش نام رانندگان) با کشیدن ماوس یا دو کلیک؛ فرم با زمان‌های انتخاب‌شده باز می‌شود؛ انتخاب بازه چیزی را رزرو نمی‌کند. حداکثر بازه آینده توسط مدیر سیستم قابل تنظیم (مثلاً ۳۰/۶۰/۹۰ روز).
- وضعیت‌های درخواست: در انتظار بررسی، تأییدشده، ردشده (با علت)، تبدیل‌شده به مأموریت، لغوشده توسط درخواست‌کننده. «درخواست‌های مأموریت من»: تمام مراحل، تاریخ تغییر وضعیت، علت رد، توضیحات اپراتور، سابقه ارسال مجدد (تاریخچه غیرقابل ویرایش).
- بررسی: **مدیر ناوگان تأیید/رد می‌کند** (اپراتور دارای مجوز نیز مطابق مجوز تعریف‌شده)؛ رد با علت الزامی؛ درخواست‌کننده می‌تواند همان درخواست را ویرایش و دوباره ارسال کند یا درخواست جدید بسازد؛ سوابق حذف نمی‌شود. درخواست‌کننده تا **قبل از شروع بررسی** می‌تواند ویرایش کند و می‌تواند درخواست تأییدنشده را مستقیماً با ذکر علت لغو کند. درخواست‌های در انتظار هیچ راننده/خودرویی را رزرو نمی‌کنند.
- پس از تأیید، اپراتور/مدیر راننده، خودرو و زمان‌بندی را تکمیل و مأموریت قطعی ثبت می‌کند.

## ۷. مأموریت

### فیلدها
شماره مأموریت (خودکار، یکتا، شمارنده هر سال شمسی از نو، مانند `۱۴۰۵-۰۰۱`؛ هرگز تکرار نمی‌شود حتی با لغو/رد)، عنوان، راننده، خودرو، مبدأ، مقاصد میانی (فهرست مرتب با افزودن/حذف/تغییر ترتیب)، مقصد نهایی، زمان شروع/پایان برنامه‌ریزی‌شده (**دقت یک ساعت**)، زمان واقعی پایان، درخواست‌کننده، گروه درخواست‌کننده، موبایل درخواست‌کننده، تعداد همراهان، هدف، توضیحات، **شماره حکم (اختیاری، متن دلخواه تا ۵۰ کاراکتر)** و **تاریخ حکم (اختیاری)**، نوع مأموریت، کیلومتر شروع/پایان هر خودرو، مسافت (محاسبه‌شده).
- فرم هوشمند: حمل بار ⟵ «شرح نوع بار و محموله»، «نام تحویل‌گیرنده»؛ حمل مسافر ⟵ «نام و نام خانوادگی مسافران (چندنفره)»، «توضیحات تکمیلی».
- ثبت مأموریت قطعی بدون **هم‌زمان راننده و خودرو** ممکن نیست.

### کنترل تداخل
- راننده یا خودرو هم‌زمان در دو مأموریت نباشد؛ مبنا **زمان برنامه‌ریزی‌شده**؛ با رسیدن پایان برنامه‌ریزی‌شده منابع آزاد می‌شوند (حتی بدون ثبت پایان واقعی).
- **فاصله اجباری** بین دو مأموریت متوالی: قابل تنظیم توسط مدیر سیستم (۰/۳۰/۶۰ دقیقه…) برای راننده و خودرو.
- تداخل → **ثبت/تمدید/تغییر مسدود** و علت دقیق (کدام راننده/خودرو، با کدام مأموریت، چه بازه‌ای) نمایش داده شود.
- پیاده‌سازی **در سطح پایگاه داده/تراکنش اتمیک** (نه فقط UI) با کنترل همروندی برای کاربران هم‌زمان.
- وضعیت‌های «غیرفعال/مرخصی/خاتمه کار» راننده و «تعمیرگاه/خارج از سرویس» خودرو مانع تخصیص‌اند.

### چرخه عمر
`برنامه‌ریزی‌شده` → (خودکار در زمان شروع) `در حال اجرا` → (خودکار با گذشتن زمان پایان یا ثبت زودهنگام اپراتور) `خاتمه‌یافته` ؛ `در انتظار تأیید انصراف` و `لغوشده`.
- شروع خودکار است؛ زمان شروع واقعی جدا ثبت نمی‌شود. با پایان برنامه‌ریزی‌شده، زمان پایان واقعی = پایان برنامه‌ریزی‌شده. **خاتمه زودهنگام** توسط اپراتور؛ راننده/خودرو بلافاصله آزاد می‌شوند ولی نوار روی تایم‌لاین باقی می‌ماند. کیلومتر پایان می‌تواند بعداً ثبت شود (تا آن زمان مسافت نهایی محاسبه نمی‌شود).
- **لغو مستقیم** توسط مدیر ناوگان/اپراتور مجاز در هر مرحله: علت الزامی، آزادسازی فوری منابع، حذف از تایم‌لاین فعال، حفظ سوابق (علت، لغوکننده، زمان). تأیید (Confirm) پیش از عملیات برگشت‌ناپذیر (لغو، بایگانی).
- **انصراف درخواست‌کننده** (فقط برای مأموریت‌های خودش؛ نه برای پایان‌یافته/لغوشده؛ علت الزامی): وضعیت «در انتظار تأیید انصراف»، منابع همچنان رزرو، نوار روی تایم‌لاین با رنگ/علامت هشدار متفاوت، **پیام فوری روی صفحه مدیر و اپراتورها**. تأیید ⟵ لغو + آزادسازی + حذف از تایم‌لاین؛ رد ⟵ بازگشت به وضعیت قبلی (برنامه‌ریزی‌شده یا در حال اجرا). اگر زمان پایان در انتظار فرا رسد ⟵ مأموریت خودکار لغو، منابع آزاد، درخواست انصراف بسته (غیرقابل بررسی) با حفظ سوابق.
- **تمدید**: اپراتور دارای مجوز مستقیماً (علت الزامی، ثبت زمان قبلی/جدید، کاربر، زمان)؛ در صورت تداخل یا نقض فاصله مسدود.
- **تغییر اطلاعات پس از تأیید** (حتی در حال اجرا): ویرایش مستقیم توسط مدیر/اپراتور مجاز، یا **درخواست تغییر** توسط درخواست‌کننده برای هر فیلد؛ تغییر زمان/راننده/خودرو باید دوباره از نظر تداخل بررسی شود؛ تا تأیید، اطلاعات قبلی معتبر است؛ **اعمال یکجا (اتمی)**؛ مدیر ناوگان یا اپراتور مجاز، هرکدام زودتر (حالت «در حال بررسی» برای جلوگیری از تصمیم دوباره)؛ رد ⟵ مأموریت دست‌نخورده، علت حفظ، امکان ثبت درخواست تغییر جدید؛ مهلت انقضا ندارد و درخواست‌های معوق برجسته می‌شوند. همه مراحل در تاریخچه.
- **تقسیم مأموریت (تعویض راننده و/یا خودرو در میانه مسیر)**: به‌جای جایگزینی، **مأموریت به دو مأموریت مستقل** (هرکدام شماره مستقل، بدون مأموریت «مادر») تقسیم می‌شود. فقط در وضعیت «در حال اجرا»، با مجوز مستقل «تقسیم» (اپراتور/مدیر ناوگان)، بدون نیاز به تأیید مجدد، مشروط به کنترل تداخل/وضعیت/فاصله/کیلومتر. زمان تقسیم با **دقت ساعت**؛ پایان مأموریت اول = شروع دوم؛ ویرایش این زمان فقط با مجوز مدیر ناوگان. ثبت **کیلومتر پایان خودروی اول الزامی**؛ کیلومتر شروع بخش دوم: اگر خودرو همان است خودکار از پایان بخش اول، وگرنه دستی و کنترل‌شده با آخرین کیلومتر آن خودرو. علت تقسیم الزامی از فهرست قابل مدیریت در تنظیمات (خرابی خودرو، تعویض راننده، تعویض هم‌زمان، سایر + توضیح آزاد؛ دلایل قدیمی با غیرفعال شدن حذف نمی‌شوند). فیلد توضیحی اختیاری برای ارتباط («ادامه مأموریت شماره …»). هر دو ردیف در فهرست با نشان «تقسیم‌شده» و نمایش علت/شماره مرتبط؛ هر دو مستقل در گزارش‌ها شمرده می‌شوند. اعلان داخل سامانه به رانندگان، اپراتورهای مرتبط و مدیر ناوگان؛ **پیامک جدیدی برای این رویداد نیست** و گزارش مستقل تقسیم ایجاد نمی‌شود. کیلومتر شروع/پایان هر بخش مستقل؛ هر دو مأموریت پس از تقسیم قابل اصلاح (با کنترل مجدد).

### کیلومتر
- کیلومتر شروع و پایان فقط توسط **اپراتور یا مدیر ناوگان** (نه راننده) ثبت/اصلاح می‌شود. مسافت = پایان − شروع (خودکار) با امکان اصلاح دستی توسط مجاز همراه تاریخچه (قبل/بعد/کاربر/زمان).
- کنترل‌ها: پایان ≥ شروع؛ شروع ≥ آخرین کیلومتر ثبت‌شده همان خودرو؛ **پیوستگی در کل برنامه مأموریت‌های هر خودرو بر اساس ترتیب زمانی**؛ اصلاحی که تناقض ایجاد کند مسدود شود با علت فارسی.
- **ساعات کارکرد**: عادی/تمدیدشده = شروع تا پایان برنامه‌ریزی‌شده (نهایی)؛ پایان زودهنگام = تا زمان ثبت؛ لغو حین اجرا = تا زمان لغو؛ لغو پیش از شروع = صفر.

### حکم مأموریت (چاپ)
- پس از ثبت/نهایی‌شدن توسط اپراتور: **پیش‌نمایش** ⟵ چاپ یا ذخیره PDF، **A4 عمودی**، فارسی/RTL با پشتیبانی فونت فارسی.
- قالب قابل تنظیم توسط مدیر سیستم بدون تغییر کد (سربرگ، لوگو، متن‌های ثابت، چیدمان، محل امضاها). محتوا: نام/لوگوی سازمان، شماره مأموریت و (در صورت وجود) شماره/تاریخ حکم، درخواست‌کننده/راننده/خودرو، نوع و هدف، مبدأ/میانی/نهایی به ترتیب، زمان‌ها. **چهار محل امضا (خالی برای امضای دستی)**: درخواست‌کننده، مسئول ناوگان/اپراتور، مدیر/مقام تأییدکننده، راننده. امضای الکترونیکی وجود ندارد.

## ۸. تایم‌لاین (هسته اصلی)

- تقویم **شمسی**، شروع هفته **شنبه**، RTL، ساعت رسمی ایران، کوچک‌ترین واحد: ۱ ساعت.
- **نمای ثابت بر اساس رانندگان** (هر راننده یک ردیف؛ بدون جابه‌جایی به نمای خودرو). ابتدای ردیف: نام و نام خانوادگی، موبایل، وضعیت راننده (رانندگان غیرقابل‌تخصیص مشخص).
- مقیاس‌ها: ساعتی، روزانه، هفتگی، ماهانه. زوم با چرخ ماوس و دکمه‌های +/− (**حول موقعیت نشانگر ماوس**). حرکت با اسکرول افقی و دکمه‌های روز/بازه قبل و بعد.
- نوار مأموریت: فقط عنوان (کوتاه‌شده با «…» متناسب با عرض)، رنگ بر اساس وضعیت مأموریت، **نوار پیوسته** برای مأموریت چندروزه حتی با عبور از نیمه‌شب. کلیک ⟵ **پنل جزئیات سمت راست** (عنوان کامل، همه اطلاعات و عملیات: ویرایش، خاتمه زودهنگام، تمدید، لغو، تقسیم، حکم، تاریخچه).
- مأموریت لغوشده/انصراف تأییدشده از تایم‌لاین فعال حذف می‌شود؛ «در انتظار تأیید انصراف» با رنگ/علامت متفاوت می‌ماند؛ مأموریت خاتمه‌یافته روی تایم‌لاین می‌ماند. تأخیر (گذشتن از پایان) ⟵ خودکار خاتمه‌یافته.
- **انتخاب بازه** با کشیدن ماوس یا دو کلیک، برای اپراتور (ساخت مأموریت قطعی بعد از انتخاب راننده/خودرو) و درخواست‌کننده (تایم‌لاین عمومی بدون نام رانندگان؛ ساخت درخواست).
- تغییرات به‌صورت زنده (SignalR) فقط برای کاربران مجاز؛ زمان‌ها فقط با دقت ساعت.

## ۹. اعلان‌های داخلی

- **۸ رویداد**: درخواست جدید (اپراتورها)، تأیید/رد درخواست (درخواست‌کننده)، تبدیل به مأموریت قطعی (درخواست‌کننده)، تمدید/تغییر زمان (افراد مرتبط)، لغو (افراد مرتبط)، نزدیک شدن شروع (راننده و اپراتور)، **پایان مأموریت (فقط مدیر ناوگان و اپراتورهای مرتبط؛ نه درخواست‌کننده)**، پیشنهاد مکان جدید (مدیر سیستم). افزون بر این: انصراف (پیام فوری)، درخواست تغییر، تقسیم مأموریت، درخواست‌های معوق.
- بخش «اعلان‌ها» دائمی با تاریخچه + **Toast** هنگام رویداد + شمارنده خوانده‌نشده + علامت‌گذاری خوانده‌شده؛ ارسال فقط به افراد مرتبط و مجاز.

## ۱۰. پیامک (آتیه داده‌پرداز – ADP)

- اتصال **سمت سرور** به وب‌سرویس SOAP با WSDL: `https://www.payamsms.com/services/v2/service.wsdl`.
- متدها: `Send(organization, username, password, srcNumber, body, destNo[])` (حداکثر ۲۵۰ گیرنده؛ شماره عددی با کد کشور، حداکثر ۱۲ رقم مثل ‎98912…‎؛ نوع فارسی/لاتین خودکار؛ خروجی `SendResult{ID, Mobile}`)، `getStatuses_OriginalID(organization?, username, password, ids[])` برای وضعیت تحویل (`DeliveryResult{ID, checkID, status}`)، `Balance(...)` برای اعتبار. (امضای دقیق باید از WSDL خوانده شود؛ حدس نزن.)
- اطلاعات اتصال (organization, username, password, srcNumber ثابت) در **ویزارد توسط مدیر فنی** وارد و در SQL ذخیره می‌شود؛ در پنل عادی **قابل مشاهده/تغییر نیست**. دکمه بررسی اعتبار (Balance) فقط برای مسئول فنی؛ پیامک آزمایشی ارسال نمی‌شود.
- **رویدادهای پیامکی (۹)**: تأیید مأموریت (پس از تأیید و تعیین نهایی راننده و خودرو)، رد درخواست، تغییر زمان/مشخصات، تغییر راننده/خودرو، لغو مأموریت، تأیید انصراف، رد انصراف، یادآوری پیش از شروع، پایان مأموریت. هر رویداد توسط مدیر سیستم فعال/غیرفعال می‌شود و **گیرندگان هر رویداد** (درخواست‌کننده، راننده یا هر دو) مستقل قابل تنظیم است. گیرنده‌ها: موبایل درخواست‌کننده از پرونده مأموریت، موبایل راننده از پرونده راننده. **زمان یادآوری قابل تنظیم** (مدیر سیستم)؛ با تغییر زمان شروع، یادآوری ارسال‌نشده قبلی لغو و دوباره برنامه‌ریزی می‌شود (ارسال‌شده‌ها در سوابق می‌ماند).
- **قالب متن هر رویداد جدا و ویرایش‌پذیر** با متغیرها: شماره/عنوان مأموریت، شماره/تاریخ حکم، درخواست‌کننده، نام و موبایل راننده، مشخصات و پلاک خودرو، مبدأ/مقصد/مسیر، تاریخ و ساعت شروع/پایان، نوع مأموریت، علت لغو/رد/انصراف.
- **صف ارسال**: خطای موقتی ⟵ تلاش مجدد خودکار (تعداد و فاصله قابل تنظیم) سپس «ارسال ناموفق» و **ارسال مجدد دستی اپراتور مجاز**؛ خطای دائمی (مثل E43 شماره نامعتبر، E6 اعتبار ناکافی، E5/E4 اطلاعات اتصال/دسترسی، E223 شماره فرستنده، E211, E132, E800 …) بدون تکرار ثبت و گزارش شود. خطا هرگز مانع عملیات مأموریت نمی‌شود؛ اعلان داخلی همیشه حفظ می‌شود.
- **پیگیری تحویل**: استعلام دوره‌ای (فاصله و حداکثر تعداد استعلام در **تنظیمات سرور/مسئول فنی**)؛ دو وضعیت مجزا: «پذیرش درخواست» و «تحویل»؛ اگر قطعی نشد «نامشخص».
- **گزارش پیامک‌ها** (فقط داخل سامانه، بدون خروجی فایل، با مجوز مستقل): گیرنده، موبایل، رویداد، متن، زمان، تعداد تلاش، وضعیت پذیرش/تحویل، شناسه ADP، علت خطا؛ فیلتر تاریخ، شماره، رویداد، وضعیت، شماره مأموریت، نوع خطا.

## ۱۱. گزارش‌ها (با مجوز، فیلتر و خروجی Excel و PDF)

۸ گزارش: کیلومتر ماهانه هر راننده؛ کیلومتر هر خودرو؛ تعداد مأموریت هر راننده/خودرو؛ مجموع ساعات هر راننده؛ **مقایسه/عدالت توزیع** (سه شاخص هم‌زمان: کیلومتر، تعداد مأموریت، ساعات)؛ مأموریت‌های بار و مسافر؛ مأموریت‌های لغوشده با علت؛ درخواست‌های تأییدشده و ردشده.
فیلترها: بازه تاریخ دلخواه، راننده، خودرو، نوع، واحد سازمانی، وضعیت. اعداد/تاریخ شمسی و فارسی. (گزارش‌های ممیزی، پیامک و نشست‌ها خروجی فایل ندارند.)

## ۱۲. ممیزی و سوابق

- **Audit Log**: همه عملیات مهم (ایجاد، ویرایش، حذف/غیرفعال‌سازی، تأیید، رد، لغو، تقسیم، تمدید، تغییر دسترسی/نقش، تغییر کیلومتر…) با کاربر، نوع، زمان، موجودیت/رکورد، **مقدار قبل/بعد**، نتیجه؛ **دائمی، غیرقابل ویرایش/حذف**؛ مشاهده با مجوز مستقل؛ جست‌وجو و فیلتر (کاربر، نوع عملیات، بازه، موجودیت، نتیجه) و مشاهده جزئیات؛ بدون Excel/PDF.
- **سوابق نشست/ورود**: نام کاربری، ورود/خروج، روش ورود (Windows/فرم)، انقضای خودکار، ورود ناموفق، IP؛ دائمی؛ مجوز مستقل؛ جدا از ممیزی.

## ۱۳. تنظیمات سامانه (فقط مدیر سیستم)

بخش واحد «تنظیمات سامانه»: نام سازمان و لوگو (در سربرگ، صفحه ورود، حکم)، تقویم/ساعت، فاصله اجباری بین مأموریت‌ها، حداکثر بازه آینده درخواست، مدت نشست و عدم فعالیت، دلایل تقسیم، فهرست واحدها، تأیید مکان‌ها، قالب‌ها/رویدادها/گیرندگان و زمان یادآوری پیامک، قالب حکم، تنظیمات AD (گروه‌های مجاز و نگاشت نقش). اطلاعات اتصال پیامک و پارامترهای استعلام تحویل خارج از پنل عادی‌اند (بخش ۱۰).

## ۱۴. داشبورد و رابط کاربری

- پس از ورود: **داشبورد اختصاصی نقش/مجوز** + کارت‌های آماری و نمودار (مأموریت‌های در انتظار، فعال، خودروهای آماده، رانندگان فعال، انصراف‌های در انتظار، پیامک‌های ناموفق برای مجازها، درخواست‌های معوق، مأموریت ماهانه، کارکرد رانندگان، وضعیت خودروها). هر کاربر **ترتیب/چیدمان کارت‌ها را شخصی‌سازی** و ذخیره می‌کند. هیچ اطلاعات خارج از سطح دسترسی نمایش داده نشود.
- محتوای پیشنهادی هر نقش: مدیر سیستم (وضعیت کلی/کاربران/تنظیمات)، مدیر ناوگان (خودروها، رانندگان، مأموریت‌ها، آمار)، اپراتور (درخواست‌های جدید، مأموریت‌های جاری، تداخل‌ها، برنامه روز)، درخواست‌کننده (ثبت و پیگیری درخواست، اعلان‌ها)، مشاهده‌گر (فقط‌خواندنی).
- سبک: **مدرن و مینیمال با کارت و نمودار**، فارسی کامل RTL، منوی راست، **تم سبز تیره + طلایی ملایم** (سبز روشن برای وضعیت‌های مثبت)، **حالت روشن و تاریک** انتخابی هر کاربر در تنظیمات شخصی (همه اجزا از جمله نمودار/جدول/تقویم هماهنگ).
- جدول‌های حرفه‌ای با جست‌وجو/فیلتر برای رانندگان، خودروها و مأموریت‌ها. پیام تأیید فقط پیش از عملیات مخرب/برگشت‌ناپذیر.

## ۱۶. نکات فنی تکمیلی

- ماشین حالت (State Machine) صریح برای مأموریت/درخواست/انصراف/تغییر؛ سرویس پس‌زمینه (HostedService) برای شروع/پایان خودکار، آزادسازی منابع، لغو خودکار انصراف منقضی، صف پیامک، یادآوری و استعلام تحویل.
- Concurrency: تراکنش و قفل/Constraint/RowVersion برای جلوگیری از تخصیص هم‌زمان؛ شماره‌گذاری سالانه بدون تکرار.
- کتابخانه تاریخ شمسی معتبر (مثل PersianCalendar/Parsi) و فونت فارسی؛ تولید PDF سازگار با RTL.
- Unit/Integration Test برای قواعد دامنه (تداخل، فاصله، کیلومتر، چرخه عمر، تقسیم، اولویت Deny، وضعیت خودرو). CI با GitHub Actions (Build + Test).
- تست‌های Windows Authentication، LDAPS و IIS فقط روی محیط واقعی ممکن است؛ در گزارش پیشرفت صریحاً ذکر شود.

## ۱۷. وضعیت فعلی پیاده‌سازی (شاخه develop، بررسی‌شده از روی کد)

> منبع: خواندن کد و مستندات مخزن (حدود ۱۵۸ فایل و ۲۱ هزار خط). «پیاده‌سازی‌شده» یعنی کد وجود دارد؛ **نه** اینکه روی محیط واقعی تست شده است. وضعیت CI را همیشه از GitHub Actions (`build.yml`: Build + Test روی Ubuntu و Windows) بررسی کنید.

### پیاده‌سازی‌شده در کد
- ویزارد راه‌اندازی، Administrator محلی، بازیابی، تنظیمات AD/سازمان/پیامک.

- چرخه کامل درخواست و مأموریت در `Mission.cs`: بررسی، تأیید، رد، شروع/پایان خودکار، تمدید، خاتمه زودهنگام، کیلومتر، انصراف، لغو، تقسیم، اعمال تغییرات.

- ۱۱ جدول در `FleetDbContext`؛ مستندات استقرار و چک‌لیست پذیرش در `docs/`.

## ۲۰. اصلاحات و تعارض‌های محاوره (تصمیم نهایی)

1. شماره حکم: ابتدا خودکار پیشنهاد شد ⟵ **نهایی: اختیاری، دلخواه تا ۵۰ کاراکتر**؛ شماره مأموریت خودکار است.
2. بررسی درخواست: ابتدا اپراتور ⟵ در چرخه عمر نهایی، **مدیر ناوگان** تأیید/رد می‌کند (اپراتور دارای مجوز نیز طبق تنظیم مجوزها).
3. تعویض راننده/خودرو: ابتدا جایگزینی با «راننده/خودرو نهایی» ⟵ **نهایی: تقسیم به دو مأموریت مستقل**، کیلومتر هر خودرو جدا.
4. دقت زمان: ساعتی در همه جا، **حتی زمان تقسیم**.
5. اعلان‌های درخواست‌کننده: پایان مأموریت برای او ارسال نمی‌شود.
6. پیامک: ابتدا «فقط اعلان داخلی» ⟵ **نهایی: اعلان داخلی + پیامک** (۹ رویداد).
7. اطلاعات پیامک: در ویزارد توسط مدیر فنی، در SQL، غیرقابل‌مشاهده در پنل؛ پارامترهای استعلام تحویل در تنظیمات سرور.
8. گزارش ممیزی/پیامک بدون خروجی فایل؛ گزارش مستقل تقسیم نداریم.
9. نمای تایم‌لاین: فقط رانندگان (ثابت). طراحی دسکتاپ‌محور. SQL Authentication و رمز‌های بدون رمزنگاری در SQL (پذیرش ریسک).
10. فاصله اجباری و بازه آینده و مدت نشست: قابل تنظیم توسط مدیر سیستم.
11. کاتالوگ مرکزی مجوزها: کلیدهای مجوز در `PermissionCatalog` لایه Application ثبت و تخصیص کلید ناشناخته رد می‌شود. مجوزهای مستقل کیلومتر، ویرایش زمان تقسیم، بررسی انصراف/درخواست تغییر، مدیریت کاربران/سامانه/مکان‌ها، قالب حکم و دلایل تقسیم تعریف می‌شوند. پیش‌فرض‌ها مطابق پیوست ب است؛ `settings.sessions` (مدیریت مدت نشست) و `security.sessions.view` (مشاهده سوابق) دو مجوز مستقل‌اند. مجوزهای مدیریتی قالب حکم و دلایل تقسیم در فضای نام `settings.*` قرار می‌گیرند تا با wildcard `missions.*` اعطا نشوند.
12. حکم مأموریت: تولید PDF سمت سرور انجام نمی‌شود؛ خروجی PDF از قابلیت چاپ مرورگر و گزینه Save as PDF تهیه می‌شود.
13. چیدمان محل امضا در قالب چاپ قابل تنظیم است و فقط دو حالت یک‌ستونه یا دوستونه پشتیبانی می‌شود.

| Pending/UnderReview | CancelPendingRequest (درخواست‌کننده) | Cancelled | فقط درخواست‌کننده خود؛ علت؛ بدون رزرو منابع |

نهایی: Completed، Cancelled، Rejected. انصراف فقط از Confirmed/Running درخواست می‌شود؛ Pending/UnderReview با لغو مستقیم درخواست‌کننده بسته می‌شود. مدیر ناوگان/اپراتور مجاز می‌تواند هر وضعیت غیرنهایی، از جمله WithdrawalPending، را مستقیماً لغو کند.

### MissionChangeRequest
Pending → (StartReview: بازبین اول) → UnderReview → Approved (اعمال اتمی) یا Rejected (علت). فقط بازبین آغازکننده می‌تواند تصمیم بگیرد؛ رد، مأموریت را دست‌نخورده می‌گذارد و درخواست جدید ممکن است.

### SmsQueueItem
Queued → Sending → Accepted → Delivered؛ خطای موقت → RetryScheduled (تا MaximumRetryCount) → Sending؛ پایان تلاش‌ها → Failed؛ خطای دائمی → PermanentFailure؛ لغو یادآوری قبل از ارسال → Cancelled. استعلام تحویل تا MaximumStatusPollingAttempts؛ **نگاشت وضعیت‌های ADP هنوز نیازمند نمونه واقعی است.**
رویدادهای پیامک (۹): MissionApproved، MissionRejected، MissionChanged، DriverOrVehicleChanged، MissionCancelled، WithdrawalApproved، WithdrawalRejected، MissionStartReminder، MissionCompleted.
