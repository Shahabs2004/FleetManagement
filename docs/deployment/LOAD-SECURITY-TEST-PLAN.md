# برنامه آزمون بار و امنیت FleetManagement

> **وضعیت: برنامه پیشنهادی؛ اجرا و نتیجه تا تکمیل توسط مالک/QA/امنیت تأییدنشده است.** این سند مجوز اجرای آزمون تهاجمی روی Production نیست. آزمون‌ها ابتدا روی محیط آزمایشی همسان با Production و با داده مصنوعی اجرا شوند. هر آزمون روی محیط واقعی فقط با مجوز کتبی مالک، پنجره تغییر و هماهنگی زیرساخت انجام شود.

## هدف و مسئولیت

هدف، اندازه‌گیری ظرفیت و پایداری سامانه، کشف خطاهای دسترسی و بررسی حفاظت از داده در استقرار سازمان است؛ نه اثبات امنیت مطلق.

| مسئول | مسئولیت |
|---|---|
| مالک سامانه | تصویب محدوده، پنجره آزمون، معیارهای پذیرش و تصمیم Go/No-Go |
| QA/آزمونگر بار | طراحی داده مصنوعی، اجرای سناریوها، ثبت نتایج و شناسه رخداد |
| مسئول امنیت | بازبینی کنترل‌های امنیتی، مجوز آزمون و مدیریت یافته‌ها |
| مدیر زیرساخت/IIS | پایش Windows/IIS/شبکه، محدودیت منابع و توقف اضطراری |
| DBA | پایش SQL، تهیه Backup پیش از آزمون و بررسی سلامت پایگاه |
| مدیر فنی | بررسی لاگ برنامه، SignalR، صف پیامک و رفع اشکال |

## پیش‌نیازهای مشترک

- نسخه برنامه، commit SHA، تنظیمات غیرمحرمانه و مشخصات محیط ثبت شوند.
- محیط آزمایش از Production جدا و تا حد امکان از نظر IIS، Hosting Bundle، SQL Server، گواهی و شبکه همسان باشد.
- داده‌ها، کاربران، شماره‌ها، نام‌ها و مأموریت‌ها مصنوعی باشند؛ داده واقعی سازمان را برای آزمون بار کپی نکنید.
- حساب آزمایشی جداگانه برای هر نقش و حساب‌های فاقد مجوز آماده شوند.
- پیش از آزمون یک Backup قابل بازیابی توسط DBA تأیید شود؛ Restore تمرینی در محیط جدا باشد.
- ابزارها و IPهای مولد بار توسط زیرساخت مجاز و در Firewall/مانیتورینگ شناسایی شوند.
- آزمون پیامک واقعی و تماس انبوه ADP جزو آزمون بار نیست. صف پیامک در محیط آزمون باید غیرفعال، شبیه‌سازی یا به سرویس آزمایشی محدود شود؛ ارسال واقعی فقط در آزمون مجزای کنترل‌شده انجام می‌شود.
- آستانه‌های عملکردی سازمان (حداکثر زمان پاسخ، خطا، CPU/Memory/SQL و ظرفیت) پیش از اجرا توسط مالک تعیین شوند. SPEC عدد عملکردی مصوبی ارائه نمی‌کند؛ بنابراین این سند SLA یا آستانه دلخواه را الزام نمی‌کند.

## برنامه پیشنهادی آزمون بار

### پروفایل بار

پروفایل اولیه پیشنهادی برای بررسی ظرفیت ۲۰ تا ۵۰ کاربر هم‌زمان است؛ این بازه در ماتریس پذیرش فعلی آمده و باید پیش از اجرا توسط مالک تأیید شود.

| مرحله | کاربران هم‌زمان | هدف |
|---|---:|---|
| Smoke | ۱ تا ۲ | صحت ورود و گردش پایه |
| Ramp-up | ۵، ۱۰، ۲۰ | مشاهده روند مصرف منابع و زمان پاسخ |
| ظرفیت هدف | ۲۰ تا ۵۰ | آزمون بار معمول سازمان؛ نقطه دقیق با مالک تعیین شود |
| Soak | ظرفیت مصوب ثابت | کشف نشت حافظه، رشد صف و افت تدریجی |
| Spike | جهش کنترل‌شده تا سقف مصوب | بررسی رفتار ازدحام و بازیابی |
| Recovery | بازگشت به بار کم | بررسی آزاد شدن منابع و بازیابی سرویس |

مدت هر مرحله، نرخ درخواست و سقف کاربران باید پیش از اجرا در طرح آزمون ثبت و با مالک هماهنگ شود. ابتدا روی Staging اجرا کنید؛ از اجرای Spike یا Soak بدون مانیتورینگ و امکان توقف خودداری کنید.

### سناریوها

1. **ورود و نشست:** ورود موفق حساب آزمایشی، ورود ناموفق، خروج، انقضای نشست و ورود مجدد؛ نرخ درخواست و زمان پاسخ ثبت شود.
2. **داشبورد و فهرست‌ها:** بارگذاری داشبورد، رانندگان، خودروها و مکان‌ها با صفحه‌بندی/فیلتر؛ تعداد درخواست و مصرف SQL ثبت شود.
3. **گردش مأموریت:** ثبت درخواست، بررسی/تأیید، شروع و پایان با داده مصنوعی؛ صحت وضعیت و زمان‌ها پس از بار بررسی شود.
4. **تعارض هم‌زمان:** درخواست‌های هم‌زمان با راننده/خودروی یکسان اجرا شوند؛ تنها نتیجه سازگار با قاعده دامنه پذیرفته و رزرو متعارض ایجاد نشود.
5. **گزارش و خروجی:** اجرای گزارش‌های پرتکرار و Excel با بازه داده مصنوعی؛ زمان پاسخ، مصرف حافظه و بار SQL پایش شود.
6. **SignalR/اعلان:** چند نشست آزمایشی، اعلان برای کاربر هدف، قطع/وصل ارتباط و همگام‌سازی مجدد؛ نشت اعلان بین کاربران نباید رخ دهد.
7. **پایداری:** در طول Soak تعداد خطا، 5xx، قطع مدار Blazor، رشد حافظه، طول صف و زمان پاسخ ثبت شود.
8. **اختلال کنترل‌شده:** در Staging قطع موقت SQL یا شبکه با هماهنگی DBA انجام شود؛ رفتار خطا و بازیابی بررسی شود. در Production اختلال عمدی ایجاد نکنید.

### معیار پذیرش بار

- معیارهای p50/p95/p99، throughput، نرخ خطا و مصرف منابع باید قبل از اجرا توسط مالک تعیین شوند؛ نتیجه با همان معیارها مقایسه شود.
- هیچ رزرو متعارض راننده/خودرو یا تغییر وضعیت نامعتبر ایجاد نشود.
- پس از پایان بار، داده‌ها و قیود دامنه معتبر بمانند و صف‌ها به وضعیت قابل کنترل برگردند.
- خطاهای 5xx، timeout، قطع SignalR، رشد حافظه و فشار SQL ثبت و با آستانه مصوب مقایسه شوند.
- سرویس پس از کاهش بار به وضعیت پایدار بازگردد؛ restart ناخواسته یا نیاز به مداخله خارج از طرح باید ثبت شود.
- نتیجه ناموفق یا معیار تعریف‌نشده، پذیرش موفق محسوب نمی‌شود.

## برنامه آزمون امنیت

### ابزارهای پیشنهادی

- **OWASP ZAP:** اسکن Passive روی محیط آزمایشی؛ Active Scan فقط با مجوز صریح و داده مصنوعی.
- **Burp Suite Community/Professional:** بررسی دستی درخواست‌ها، نشست و کنترل دسترسی؛ فقط در محدوده مجاز.
- **k6 یا Apache JMeter:** بار HTTP و سناریوهای کاربری؛ انتخاب ابزار با QA.
- **Browser DevTools:** بررسی کوکی، TLS، درخواست‌های Blazor/SignalR و خطاهای سمت کاربر.
- **IIS logs، Event Viewer، Windows Performance Monitor و SQL Server Query Store/مانیتورینگ DBA:** همبستگی خطا و منابع.
- ابزارها باید از نسخه معتبر و محیط کنترل‌شده استفاده شوند؛ هیچ ابزار اسکن/تست به Production بدون مجوز اجرا نشود.

### سناریوهای امنیتی و معیار پذیرش

1. **احراز هویت:** حساب فعال/غیرفعال/قفل‌شده/غیرمجاز و ورود Windows/AD طبق سیاست سازمان؛ حساب غیرمجاز نشست معتبر نگیرد.
2. **مجوزدهی افقی و عمودی:** حساب فقط‌مشاهده، اپراتور و مدیر با تلاش مستقیم برای URL/endpointهای خارج از مجوز آزموده شوند؛ عدم مجوز نباید با مخفی‌کردن دکمه جایگزین شود.
3. **جداسازی داده:** کاربر A نباید اعلان، سوابق یا داده اختصاصی کاربر B را ببیند؛ Hub اعلان‌ها باید احراز هویت‌شده باقی بماند.
4. **CSRF و درخواست‌های تغییر‌دهنده:** درخواست‌های فاقد توکن/نشست معتبر طبق مکانیزم برنامه رد شوند؛ عملیات تغییر وضعیت با نشست کاربر دیگر پذیرفته نشود.
5. **ورودی و خروجی:** ورودی‌های طولانی، نامعتبر و دارای کاراکترهای ویژه در فرم‌ها/فیلترها آزمایش شوند؛ XSS بازتابی/ذخیره‌شده و تزریق SQL نباید رخ دهد.
6. **محدودیت ورود:** مستندات فعلی سقف ۱۰ درخواست در دقیقه برای هر IP و پاسخ HTTP 429 را مشخص می‌کند. با نرخ کنترل‌شده آزمون شود؛ اثر in-memory بودن limiter و restart نیز ثبت شود.
7. **Reverse Proxy:** فقط Proxy مورد اعتماد باید Forwarded Headers را تعیین کند؛ هدر جعلی از منبع غیرمجاز نباید IP مبنای محدودسازی را جعل کند.
8. **TLS و Headerها:** اعتبار گواهی، HTTPS، HSTS در محیط غیرتوسعه، کوکی‌های نشست و Headerهای امنیتی بررسی شوند؛ نتیجه با سیاست امنیت سازمان مقایسه شود.
9. **اسرار و لاگ:** رمز AD/SQL/ADP، کد Bootstrap، Connection String، شماره و داده شخصی در پاسخ خطا، لاگ، URL یا فایل عمومی ظاهر نشود.
10. **فایل و ACL:** مسیر Bootstrap خارج از ریشه وب باشد؛ دسترسی NTFS فقط مطابق راهنمای استقرار باشد؛ فایل/Backup از طریق HTTP قابل دریافت نباشد.
11. **وابستگی‌ها و پیکربندی:** بسته‌های NuGet و تنظیمات انتشار از نظر نسخه آسیب‌پذیر، Debug/Developer Exception Page و اطلاعات اضافی خطا بازبینی شوند.
12. **ممیزی:** تغییرات حساس، ورود/خروج و رخدادهای مورد انتظار با عامل و زمان مناسب ثبت شوند؛ رمز و داده حساس در ممیزی ذخیره نشود.

### معیار توقف فوری

در صورت مشاهده افشای داده واقعی، دسترسی غیرمجاز موفق، ایجاد رزرو ناسازگار، ارسال ناخواسته پیامک واقعی، اختلال محسوس کاربران، افزایش کنترل‌نشده منابع یا خطر آسیب به داده، آزمون را فوراً متوقف و مدیر زیرساخت/مالک را مطلع کنید. شواهد را امن نگه دارید؛ داده یا لاگ را برای پاک کردن ردپا حذف نکنید.
