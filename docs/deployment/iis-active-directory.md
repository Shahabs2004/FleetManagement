# راهنمای استقرار IIS و Active Directory

این راهنما مکمل [چک‌لیست انتشار و پذیرش](RELEASE-AND-ACCEPTANCE-CHECKLIST.md) است و جزئیات میزبانی IIS، ارتباط Blazor Server، Windows Authentication، LDAPS، اتصال SQL Server و ACL فایل‌های راه‌اندازی را پوشش می‌دهد. برای جلوگیری از تکرار، ترتیب کلی انتشار و آزمون‌های پذیرش برنامه در چک‌لیست انتشار باقی می‌ماند.

> **وضعیت همه مراحل این راهنما: تأییدنشده تا اجرای مالک در محیط واقعی سازمان.** وجود تنظیمات و کد در مخزن، موفقیت استقرار روی Windows Server، IIS، دامنه و SQL سازمان را اثبات نمی‌کند. نتیجه هر اجرا باید در [ماتریس پذیرش](ACCEPTANCE-MATRIX.md) ثبت شود.

## مسئولیت‌ها و مرزهای امنیتی

| مسئول | مسئولیت |
|---|---|
| مدیر زیرساخت Windows/IIS | نصب Roleها و Hosting Bundle، ساخت Application Pool و وب‌سایت، HTTPS، WebSocket و ACL فایل‌ها |
| مدیر Active Directory | حساب سرویس خواندن دایرکتوری، گواهی LDAPS، گروه‌های مجاز و دسترسی شبکه به Domain Controller |
| مدیر پایگاه داده | ایجاد پایگاه داده و حساب SQL اختصاصی، محدودسازی شبکه و تأیید مجوزهای لازم |
| مدیر فنی سامانه | انتشار خروجی، اجرای ویزارد و آزمون یکپارچه ورود و اتصال‌ها |
| مالک/مسئول پذیرش | مشاهده شواهد و ثبت نتیجه نهایی در ماتریس پذیرش |

هیچ رمز، Connection String، نام/نشانی واقعی سرور، نام دامنه، نام کاربری سازمانی، کد مدیر فنی یا داده واقعی را در Git، اسکرین‌شات عمومی یا گزارش قابل انتشار ثبت نکنید. مقادیر واقعی فقط در محیط امن سازمان و در زمان استقرار وارد شوند.

## پیش‌نیازهای مشترک

**پیش‌نیازها**
- Windows Server پشتیبانی‌شده و به‌روزرسانی‌شده؛ نسخه دقیق باید توسط سازمان تعیین شود.
- دسترسی Administrator برای نصب Role/Feature و تنظیم IIS.
- IIS، قابلیت ASP.NET Core و WebSocket Protocol.
- .NET 10 Hosting Bundle متناسب با معماری سرور؛ نصب آن پس از نصب IIS انجام شود تا ماژول ASP.NET Core برای IIS ثبت شود.
- گواهی TLS معتبر برای نام DNS سامانه و امکان اتصال HTTPS از مرورگرهای سازمان.
- دسترسی شبکه از سرور برنامه به SQL Server و Domain Controller.
- دسترسی به خروجی انتشار معتبر و نسخه‌بندی‌شده برنامه.

**گام‌ها**
1. ساعت و به‌روزرسانی امنیتی سرور را با سیاست سازمان تطبیق دهید.
2. IIS و قابلیت‌های موردنیاز را نصب کنید؛ در IIS Manager وجود WebSocket Protocol و Windows Authentication را بررسی کنید.
3. Hosting Bundle نسخه ۱۰ را نصب کنید. اگر IIS بعد از Hosting Bundle نصب شده، نصب/Repair مربوط به Hosting Bundle را تکرار و سپس IIS را راه‌اندازی مجدد کنید.
4. گواهی HTTPS را در مخزن مناسب سرور نصب و زنجیره اعتماد آن را بررسی کنید.

**راستی‌آزمایی و نتیجه مورد انتظار**
- IIS Manager باز می‌شود و ماژول ASP.NET Core Module V2 در فهرست ماژول‌ها موجود است.
- Windows Authentication و WebSocket Protocol در Role Services نصب‌شده دیده می‌شوند.
- گواهی HTTPS معتبر، منطبق با نام DNS و دارای زنجیره اعتماد کامل است.

**مسئول:** مدیر زیرساخت.
**در صورت شکست:** استقرار را آغاز نکنید. خطای نصب Role/Hosting Bundle یا زنجیره گواهی را با تیم زیرساخت رفع کنید؛ اعتبارسنجی TLS را غیرفعال نکنید.

## ساخت Application Pool و وب‌سایت IIS

**پیش‌نیازها**
- پیش‌نیازهای مشترک تکمیل شده باشند.
- مسیر ثابت و محدودشده برای پوشه انتشار تعیین شده باشد.
- نام Application Pool نهایی مشخص باشد؛ همین نام هنگام اجرای اسکریپت ACL استفاده می‌شود.

**گام‌ها**
1. در IIS یک Application Pool اختصاصی برای FleetManagement ایجاد کنید.
2. تنظیمات Pool:
   - **.NET CLR Version:** گزینه No Managed Code؛ اجرای .NET توسط ASP.NET Core Module انجام می‌شود.
   - **Managed pipeline mode:** Integrated.
   - **Enable 32-Bit Applications:** غیرفعال، مگر آنکه معماری خروجی و تصمیم مصوب سازمان خلاف آن باشد.
   - **Identity:** هویت اختصاصی Application Pool؛ از حساب Administrator یا حساب شخصی استفاده نکنید.
   - **Maximum Worker Processes:** مقدار 1 باقی بماند؛ برای این استقرار تک‌سروری از Web Garden استفاده نکنید.
3. خروجی انتشار را در پوشه‌ای خارج از مسیرهای قابل نوشتن کاربران عادی قرار دهید و دسترسی خواندن/اجرا را به هویت Pool بدهید.
4. یک وب‌سایت یا IIS Application مستقل به پوشه انتشار متصل کنید و Binding مربوط به HTTPS را با گواهی معتبر تنظیم کنید.
5. فایل web.config همراه خروجی Publish را در ریشه برنامه نگه دارید و آن را با تنظیمات پروژه جایگزین یا دستی بازنویسی نکنید. نسخه موجود در مخزن از AspNetCoreModuleV2 و hostingModel=inprocess استفاده می‌کند.
6. پس از تنظیم مسیر داده و نام Pool، اسکریپت آماده‌سازی ACL را طبق بخش «فایل‌های Bootstrap و ACL» اجرا کنید.

**راستی‌آزمایی و نتیجه مورد انتظار**
- Pool بدون خطا Started می‌شود و سایت از طریق HTTPS پاسخ می‌دهد.
- هویت Pool اختصاصی است و دسترسی نوشتن غیرضروری به پوشه انتشار ندارد.
- web.config در ریشه Publish وجود دارد و نام DLL آن با خروجی واقعی انتشار مطابقت دارد.
- لاگ IIS و Event Viewer خطای بارگذاری ASP.NET Core Module یا دسترسی فایل نشان نمی‌دهد.

**مسئول:** مدیر زیرساخت؛ مدیر فنی انتشار را کنترل می‌کند.
**در صورت شکست:** سایت را به کاربران معرفی نکنید. وضعیت Pool، مسیر فیزیکی، مجوز NTFS، Hosting Bundle و Event Viewer را بررسی کنید. از اعطای دسترسی Full Control عمومی یا اجرای Pool با Administrator برای رفع موقت خطا خودداری کنید.

## Blazor Interactive Server، WebSocket و SignalR

برنامه با Blazor Web App در حالت **Interactive Server** اجرا می‌شود و از SignalR برای ارتباط زنده استفاده می‌کند. در Program.cs، سرویس‌های Interactive Server و SignalR ثبت شده‌اند و Hub اعلان‌ها در مسیر /hubs/notifications با مجوز احراز هویت‌شده نگاشت می‌شود.

**پیش‌نیازها**
- WebSocket Protocol در IIS نصب و فعال باشد.
- پراکسی یا تجهیزات شبکه میانی، در صورت وجود، امکان عبور اتصال WebSocket روی HTTPS را داشته باشند.
- مرورگرهای سازمانی مورد پشتیبانی (Edge، Chrome و Firefox به‌روز) به نشانی HTTPS دسترسی داشته باشند.

**گام‌ها**
1. در Windows Features/Server Manager نصب بودن WebSocket Protocol را بررسی کنید.
2. در IIS، WebSocket را برای سایت فعال نگه دارید و هر قانون فیلتر/پراکسی را که درخواست Upgrade را حذف می‌کند اصلاح کنید.
3. HTTPS را در دسترس قرار دهید؛ اتصال Blazor Server و SignalR باید از همان مبدأ برنامه برقرار شود.
4. در صورت استفاده از Reverse Proxy، تنظیمات عبور WebSocket و Timeout را با سیاست زیرساخت هماهنگ کنید؛ Headerهای Forwarded را فقط از Proxyهای مورد اعتماد بپذیرید.
5. برنامه را با دو نشست آزمایشی مجاز باز کنید و یک تغییر داده قابل مشاهده را انجام دهید تا به‌روزرسانی زنده و اتصال مجدد بررسی شود.

**راستی‌آزمایی و نتیجه مورد انتظار**
- ابزار توسعه مرورگر، اتصال SignalR را برقرار نشان می‌دهد؛ در صورت پشتیبانی مسیر شبکه، Transport از نوع WebSocket انتخاب می‌شود.
- تغییر اعلان/داده برای نشست مجاز دیگر بدون بارگذاری کامل صفحه منعکس می‌شود.
- پس از قطع و وصل شبکه، مدار Blazor دوباره متصل و داده‌های موردنیاز همگام می‌شوند.
- Hub بدون احراز هویت قابل استفاده نیست.

**مسئول:** مدیر زیرساخت و QA؛ مدیر فنی نتیجه برنامه را بررسی می‌کند.
**در صورت شکست:** ابتدا WebSocket Feature، پاسخ Upgrade، گواهی HTTPS، Timeout و تنظیمات Proxy را بررسی کنید. اگر WebSocket در مسیر پشتیبانی نشد، رفتار Transport جایگزین SignalR را بررسی کنید؛ خطا را با غیرفعال‌کردن احراز هویت یا بازکردن Hub برای کاربران ناشناس دور نزنید.

## Windows Authentication در IIS

پیکربندی فعلی src/FleetManagement.Web/web.config هر دو مورد زیر را فعال می‌کند:
- Anonymous Authentication برای نمایش صفحه ورود جایگزین.
- Windows Authentication برای ورود یکپارچه؛ Providerها به ترتیب Negotiate و سپس NTLM هستند.

**پیش‌نیازها**
- Windows Authentication Role Service نصب باشد.
- سایت از HTTPS استفاده کند.
- مرورگرهای سازمانی برای نام سایت در محدوده مجاز Integrated Authentication قرار گرفته باشند.
- مدیر AD حساب‌های آزمایشی فعال، غیرفعال/قفل‌شده و عضو/غیرعضو گروه‌های مجاز را آماده کند.

**گام‌ها**
1. در IIS Manager، در سطح سایت/برنامه، Anonymous Authentication و Windows Authentication را مطابق web.config فعال نگه دارید.
2. Providerهای Windows Authentication را با ترتیب Negotiate و سپس NTLM تطبیق دهید؛ تغییر ترتیب یا حذف Provider فقط با تأیید مدیر AD انجام شود.
3. مطمئن شوید تنظیمات Authentication در سطح بالاتر IIS، مقدار برنامه را ناخواسته Override نمی‌کند.
4. نام سایت را طبق سیاست مرورگر سازمان در Intranet Zone یا فهرست مجاز Integrated Authentication قرار دهید.
5. ورود یکپارچه را با حساب آزمایشی مجاز و حساب‌های غیرمجاز بررسی کنید. ورود جایگزین با نام کاربری/رمز دامنه، از مسیر LDAPS انجام می‌شود و مستقل از Windows Integrated است.

**راستی‌آزمایی و نتیجه مورد انتظار**
- صفحه ورود برای کاربر ناشناس قابل نمایش است.
- مرورگر سازمانی برای حساب دامنه مجاز، احراز هویت Windows را انجام می‌دهد.
- برنامه پیش از صدور نشست، فعال‌بودن حساب و عضویت مستقیم/تودرتو در گروه‌های مجاز را بررسی می‌کند.
- حساب غیرفعال، قفل‌شده یا خارج از گروه مجاز وارد نمی‌شود؛ غیرفعال‌سازی داخلی سامانه با فعال شدن مجدد حساب AD خودکار برداشته نمی‌شود.

**مسئول:** مدیر زیرساخت و مدیر AD؛ مدیر فنی آزمون برنامه را اجرا می‌کند.
**در صورت شکست:** ابتدا نصب Feature، Authentication در سطح سایت، ترتیب Providerها و تنظیمات مرورگر را بررسی کنید. از خاموش‌کردن کنترل گروه‌های مجاز یا فعال‌کردن Anonymous به‌عنوان جایگزین Windows Authentication برای دور زدن خطا استفاده نکنید.

## اتصال امن به Active Directory از طریق LDAPS

**پیش‌نیازها**
- نشانی DNS معتبر Domain Controller و سرویس LDAPS قابل دسترس باشد.
- گواهی سرور LDAP دارای نام DNS منطبق، بازه اعتبار صحیح و زنجیره مورد اعتماد باشد.
- سرور IIS به پورت LDAPS سازمان (معمولاً TCP 636) دسترسی داشته باشد؛ پورت واقعی را مدیر AD اعلام کند.
- حساب سرویس دایرکتوری با حداقل مجوز خواندن کاربران، وضعیت حساب و گروه‌های موردنیاز آماده باشد. این حساب با هویت Application Pool یکی فرض نشود؛ اطلاعات bind در تنظیمات AD ویزارد وارد می‌شود.

**گام‌ها**
1. مدیر AD گواهی LDAPS و زنجیره CA را روی Domain Controller بررسی کند.
2. گواهی CA ریشه/میانی موردنیاز را از مسیر مورد تأیید سازمان در مخزن اعتماد Windows Server برنامه نصب کنید.
3. دسترسی شبکه از سرور برنامه به نام DNS و پورت LDAPS را بررسی کنید.
4. در ویزارد راه‌اندازی/تنظیمات AD، نشانی سرور، دامنه، تنظیمات LDAPS، حساب سرویس و گروه‌های مجاز را در محیط امن وارد کنید.
5. آزمون اتصال و سپس ورود با حساب‌های آزمایشی فعال، غیرفعال، قفل‌شده، منقضی و خارج از گروه مجاز را انجام دهید.
6. عضویت مستقیم و تودرتوی گروه‌ها و نگاشت گروه به نقش را با سیاست واقعی سازمان تطبیق دهید.

**راستی‌آزمایی و نتیجه مورد انتظار**
- اتصال TLS به LDAPS بدون خطای اعتماد گواهی و بدون هشدار نام میزبان برقرار می‌شود.
- حساب آزمایشی مجاز پس از کنترل وضعیت و گروه‌ها وارد می‌شود؛ حساب غیرمجاز رد می‌شود.
- رمز یا اطلاعات bind در لاگ، پیام خطا، اسکرین‌شات یا Git ثبت نمی‌شود.

**مسئول:** مدیر AD؛ مدیر زیرساخت اعتماد گواهی و شبکه را فراهم می‌کند؛ مدیر فنی آزمون ویزارد را انجام می‌دهد.
**در صورت شکست:** نام DNS، اعتبار و EKU گواهی، زنجیره CA، ساعت سرور و Firewall را بررسی کنید. هرگز اعتبارسنجی TLS را غیرفعال نکنید یا به LDAPS با گواهی نامعتبر تنزل ندهید. تا رفع خطا، ورود دامنه را تأییدشده اعلام نکنید.

## اتصال برنامه به SQL Server

طبق مشخصات پروژه، اتصال برنامه با **SQL Authentication** است. اطلاعات حداقلی لازم برای اتصال اولیه، به‌صورت محافظت‌شده در فایل Bootstrap محلی نگهداری می‌شود و سایر تنظیمات عملیاتی در SQL قرار می‌گیرند. برنامه ماژول Backup مستقل ندارد.

**پیش‌نیازها**
- نمونه SQL Server و نام پایگاه داده توسط مدیر پایگاه داده تعیین شده باشد.
- دسترسی شبکه از سرور IIS به Listener/Instance و پورت واقعی SQL برقرار باشد.
- حساب SQL اختصاصی سامانه ایجاد شده باشد؛ این حساب نباید sysadmin باشد.
- سیاست مجوزدهی حساب، اعمال Migration و عملیات روزمره را پوشش دهد. نقش‌ها و مجوزهای دقیق باید با Migrationهای نسخه منتشرشده و سیاست DBA تطبیق داده شوند؛ این راهنما سطح دسترسی فراتر از نیاز را تجویز نمی‌کند.

**گام‌ها**
1. مدیر پایگاه داده پایگاه اختصاصی و حساب SQL Authentication را طبق سیاست سازمان آماده کند.
2. Firewall را فقط برای مبدأهای مجاز، به‌ویژه سرور برنامه و ایستگاه‌های مدیریتی لازم، باز کند.
3. در ویزارد اولیه برنامه، سرور/Instance، نام پایگاه داده و اعتبارنامه SQL را در محیط امن وارد کنید؛ هیچ Connection String واقعی را در فایل‌های مخزن یا مستندات قرار ندهید.
4. آزمون اتصال و اجرای Migrationهای راه‌اندازی را تا نمایش نتیجه موفق دنبال کنید.
5. پس از راه‌اندازی، دسترسی شبکه و مجوزهای حساب را بازبینی کنید و نسخه پشتیبان معتبر را پیش از هر ارتقا تأیید کنید.

**راستی‌آزمایی و نتیجه مورد انتظار**
- اتصال از میزبان برنامه برقرار می‌شود.
- Migrationهای نسخه جاری بدون خطا اعمال و ساختار پایگاه داده آماده می‌شود.
- برنامه پس از راه‌اندازی مجدد IIS قادر به اتصال مجدد است.
- حساب SQL فاقد مجوز sysadmin است و فقط دسترسی‌های مصوب DBA را دارد.

**مسئول:** مدیر پایگاه داده برای حساب/پایگاه/شبکه؛ مدیر فنی برای ورود تنظیمات و آزمون برنامه.
**در صورت شکست:** خطای DNS/Instance، پورت، Firewall، مجوز Login و وضعیت Migration را با DBA بررسی کنید. مجوز sysadmin یا دسترسی شبکه گسترده را برای رفع موقت خطا اعطا نکنید. اگر Migration ناقص ماند، انتشار را متوقف و طبق رویه DBA وضعیت پایگاه را بررسی کنید.

## فایل‌های Bootstrap و ACL

برنامه فایل‌های محلی راه‌اندازی را در مسیر پیش‌فرض زیر نگهداری می‌کند:

C:\ProgramData\FleetManagement

اسکریپت موجود scripts/windows/Prepare-Server.ps1 پوشه را ایجاد می‌کند، وراثت ACL را حذف می‌کند و دسترسی‌ها را به این موارد محدود می‌کند:
- SYSTEM: Full Control
- BUILTIN\Administrators: Full Control
- IIS AppPool\<ApplicationPoolName>: Modify

هویت Application Pool برای ایجاد/حذف فایل‌های راه‌اندازی به Modify روی پوشه نیاز دارد. اسکریپت را فقط روی سرور سازمان و با نام Pool نهایی اجرا کنید.

**پیش‌نیازها**
- Application Pool نهایی در IIS ایجاد شده باشد.
- PowerShell با دسترسی Administrator اجرا شود.
- نام Pool و مسیر داده با تنظیمات واقعی استقرار تطبیق داشته باشند.

**گام‌ها**
1. اسکریپت را از نسخه کنترل‌شده مخزن دریافت و محتوای آن را بازبینی کنید.
2. در PowerShell مرتفع‌شده، دستور زیر را با نام واقعی Pool اجرا کنید:

~~~powershell
.\scripts\windows\Prepare-Server.ps1 -ApplicationPoolName "<نام-Application-Pool>"
~~~

3. اگر مسیر داده سازمانی متفاوت است، فقط پس از تأیید مدیر زیرساخت از پارامتر -DataDirectory استفاده کنید؛ مسیر نباید زیر ریشه وب باشد.
4. ACL را با دستور زیر بررسی کنید:

~~~powershell
icacls "$env:ProgramData\FleetManagement"
~~~

5. پیش از اولین اجرای برنامه، وجود پوشه و مجوز Modify هویت Pool را تأیید کنید.
6. پس از تکمیل ویزارد، حذف فایل کد خام مدیر فنی را بررسی کنید. برنامه ابتدا فایل کد را حذف می‌کند و سپس وضعیت تکمیل را ثبت می‌کند؛ اگر حذف به علت مجوز ناموفق باشد، تکمیل راه‌اندازی انجام نمی‌شود.

**راستی‌آزمایی و نتیجه مورد انتظار**
- اسکریپت بدون خطا پایان می‌یابد و فقط سه هویت فوق مجوز دارند.
- پوشه خارج از ریشه وب است و از طریق HTTP قابل دریافت نیست.
- Application Pool قادر به ایجاد/حذف فایل‌های Bootstrap موردنیاز است.
- پس از تکمیل موفق ویزارد، فایل کد خام مدیر فنی باقی نمی‌ماند.

**مسئول:** مدیر زیرساخت؛ مدیر فنی نتیجه ویزارد را کنترل می‌کند.
**در صورت شکست:** خروجی اسکریپت و icacls را بررسی کنید. اجرای برنامه را تا اصلاح ACL متوقف کنید؛ به‌صورت دستی دسترسی Everyone، Users یا حساب‌های غیرمرتبط را اضافه نکنید. ACL فایل کد را جداگانه تغییر ندهید؛ سیاست موجود برنامه به مجوز پوشه متکی است.

## عیب‌یابی مشترک

| نشانه | بررسی | رفتار ایمن در صورت شکست |
|---|---|---|
| خطای 500.30 یا شروع نشدن برنامه | Event Viewer، Hosting Bundle، معماری و مسیر DLL | سایت را از دسترس خارج نگه دارید؛ خطای واقعی را رفع و دوباره راه‌اندازی کنید |
| خطای دسترسی به فایل Bootstrap | هویت Pool و ACL پوشه ProgramData | ACL را با اسکریپت و نام Pool صحیح اصلاح کنید؛ دسترسی عمومی ندهید |
| صفحه ورود دیده نمی‌شود | Binding HTTPS، Anonymous Authentication و مسیر برنامه | تنظیم IIS را با web.config تطبیق دهید |
| Windows Authentication انجام نمی‌شود | Windows Authentication Feature، Providerها و تنظیم مرورگر | تا رفع مشکل، ورود یکپارچه را تأییدشده ندانید |
| LDAPS برقرار نمی‌شود | DNS، پورت، ساعت، اعتبار و زنجیره گواهی | TLS validation را خاموش نکنید؛ از حساب یا کانال ناامن جایگزین استفاده نکنید |
| اتصال SignalR قطع می‌شود | WebSocket Protocol، Upgrade، Proxy و Timeout | احراز هویت Hub را حذف نکنید؛ خطای Transport را ثبت و اصلاح کنید |
| SQL در دسترس نیست | مسیر شبکه، Instance/Port، حساب SQL و مجوزها | مجوز sysadmin یا بازکردن Firewall برای همه را راه‌حل ندانید |

## ثبت نتیجه و وضعیت پذیرش

- تمام مراحل این راهنما تا اجرای موفق روی محیط واقعی سازمان **تأییدنشده** هستند.
- نتیجه هر آزمون، تاریخ، نسخه برنامه، نام محیط غیرحساس، مسئول و پیوند شواهد را در [ماتریس پذیرش](ACCEPTANCE-MATRIX.md) ثبت کنید.
- رمز، Connection String، نام واقعی میزبان/دامنه، اطلاعات حساب سرویس، کد Bootstrap و داده شخصی را در ماتریس یا گزارش عمومی وارد نکنید.
- در صورت شکست، وضعیت را «تأییدنشده» نگه دارید و اقدام اصلاحی و آزمون مجدد را ثبت کنید.
