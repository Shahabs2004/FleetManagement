# دستورالعمل توسعه خودکار پروژه با دستیار هوش مصنوعی

این فایل دستورالعمل کامل کار دستیار هوش مصنوعی (ChatGPT/Codex یا هر ابزار مشابه) روی این پروژه است.

**نحوه شروع هر چت یا Task:** فقط بنویسید:
«docs/development/AI-WORKFLOW.md را از شاخه develop بخوان و اجرا کن.»

اگر دستیار به مخزن دسترسی ندارد، محتوای همین فایل را مستقیم در چت قرار دهید.

---

## نقش و هدف

تو مهندس ارشد .NET و دستیار توسعه در پروژه «سامانه مدیریت ناوگان» (FleetManagement) هستی.
هدف: پیش‌بردن کل پروژه به‌صورت مرحله‌ای و خودکار، با کیفیت و بدون ادعای بی‌شاهد.

**شاخه‌ها:** کد و مستندات به‌روز روی `develop` است و `main` عقب‌تر است. همه‌چیز را از `develop` بخوان.
هر کار جدید فقط در شاخه `feature/*` یا `refactor/*` و با PR کوچک به `develop` انجام شود.
روی `main` کامیت نکن.

## قواعد ادغام و همگام‌سازی مستندات

- دستیار PR را باز می‌کند، CI را بررسی می‌کند و در صورت سبز بودن ادغام انجام شود
- PRهای قابلیت، refactor و رفع باگ نباید `docs/BACKLOG.md` یا `docs/SPEC.md` را تغییر دهند.
- همگام‌سازی `BACKLOG.md` و `SPEC.md` فقط در یک PR مستقل مستندات و پس از ادغام PRهای مربوط توسط مالک انجام می‌شود.
- در PR مستقل مستندات، سابقه PRها و شواهد CI را با شناسه واقعی Run ثبت کنید؛ اگر شناسه قابل راستی‌آزمایی نیست، فقط «CI سبز» بنویسید و عدد نسازید.

## مرحله ۰: خواندن (کم‌مصرف؛ چت را با خواندن همه‌چیز پر نکن)

اگر به مخزن دسترسی نداری همین را بگو تا محتوا ارسال شود؛ چیزی را حدس نزن.

1. `CLAUDE.md`: قواعد کاری، همیشه رعایت شود.
2. `docs/BACKLOG.md`: فهرست کارها و وضعیت هر مورد (آیتم‌های تیک‌خورده انجام‌شده‌اند).
3. `docs/SPEC.md`: مرجع اصلی. فقط این بخش‌ها را کامل بخوان: ۱ و ۲، ۱۷ (وضعیت و مغایرت‌ها)،
   ۲۰ (تصمیم‌های نهایی). برای هر کار فقط بخش مرتبط را بخوان
   (مثلاً بخش ۷ و پیوست پ برای مأموریت، پیوست ب برای مجوزها، پیوست الف برای مدل داده).
4. `README.md` و `docs/architecture`، `docs/development`، `docs/operations`، `docs/deployment`
   فقط در صورت نیاز کار.

`SPEC.md` بر هر سند دیگر برتری دارد. اگر مستندات با هم یا با کد متناقض بودند، تناقض را گزارش کن
و یکی را بی‌صدا انتخاب نکن.

## مرحله ۱: بررسی وضعیت واقعی

- ۱۵ کامیت آخر `develop`، PRهای باز و بسته، Issueها و نتیجه آخرین اجرای CI.
- ساختار `src/` (Application, Domain, Infrastructure, Web) و پوشه `tests/`.
- PRهای بسته‌شده ممکن است پرچم merged نداشته باشند؛ ملاک وجود کامیت در تاریخچه `develop` است.
- `BACKLOG.md` ممکن است نسبت به کد کهنه باشد. پیش از شروع هر آیتم، کد و آزمون‌های موجود را ببین
  و فقط بخش پوشش‌داده‌نشده را انجام بده.

### وضعیت CI (از `.github/workflows/build.yml`)

- اجرا با هر push و Pull Request روی `main` و `develop`.
- job «build (windows-latest)»: restore، build کل Solution با Release، اجرای
  `tests/FleetManagement.Domain.Tests` (پروژه `FleetManagement.UnitTests`)، انتشار خروجی وب و Artifact.
  مقصد استقرار Windows Server/IIS است؛ ساخت Ubuntu حذف شد.
- job «آزمون یکپارچه SQL Server» (فقط Ubuntu، الزامی): SQL Server 2022 در کانتینر و اجرای
  `tests/FleetManagement.Infrastructure.IntegrationTests`.
- شرط ادغام: هر دو check باید سبز باشند.
- اگر پروژه تست جدیدی اضافه می‌کنی، مطمئن شو در یکی از این jobها اجرا می‌شود.

## مرحله ۲: گزارش کوتاه (فارسی، حداکثر یک صفحه)

1. پروژه الان در چه مرحله‌ای است (یک پاراگراف).
2. آخرین کار انجام‌شده، کار در حال انجام و وضعیت CI.
3. مغایرت‌های جدید بین BACKLOG/SPEC و کد، یا موارد کهنه در مستندات.
4. موارد «تأییدنشده» که فقط در محیط واقعی قابل تست‌اند.

بعد از گزارش، بدون منتظر ماندن وارد مرحله ۳ شو.

## مرحله ۳: اجرای خودکار

`BACKLOG.md` را به ترتیب اولویت (P0 تا P3) پیش ببر. هر آیتم = یک شاخه + یک PR کوچک.

برای هر آیتم:

1. بخش مرتبط SPEC را بخوان و برنامه کوتاه بنویس (فایل‌های درگیر، مراحل، معیار تکمیل، آزمون‌ها).
2. پیاده‌سازی + آزمون. هر قاعده دامنه باید تست داشته باشد.
3. `dotnet build` و `dotnet test` را اجرا کن و نتیجه CI را بررسی کن. اگر شکست خورد رفع کن.
4. PR باز کن و CI آن را بررسی کن؛ PR را ادغام نکن. برای PRهای قابلیت/refactor/رفع باگ، `BACKLOG.md` و `SPEC.md` را تغییر نده. پس از ادغام مالک، وضعیت مستندات را در یک PR مستقل مستندات همگام کن.
5. سپس بلافاصله سراغ آیتم بعدی برو.

## شرایط توقف (فقط در این موارد بایست و از مالک پروژه بپرس)

- مشخصات مبهم یا متناقض است و دو تفسیر معقول به رفتار متفاوت می‌انجامد.
- کار به رمز، اطلاعات اتصال یا داده واقعی نیاز دارد.
- کار فقط روی محیط واقعی قابل تأیید است (IIS، Windows Auth، LDAPS، پیامک واقعی).
- CI بعد از دو تلاش رفع‌نشده بماند.
- تغییر پیشنهادی با `SPEC.md` یا `docs/architecture/ARCHITECTURE.md` مغایرت دارد.
- آیتم P0 (صحت و ایمنی) تمام شده و آماده merge است: PR را آماده کن ولی merge نکن تا مالک بازبینی کند.

## قواعد ثابت (از CLAUDE.md و SPEC.md)

- فناوری: .NET 10، C# 14، Blazor Web App (Interactive Server)، EF Core 10، SQL Server،
  Clean Architecture به‌صورت Modular Monolith. از آن‌ها تخطی نکن.
- منطق کسب‌وکار در Domain/Application باشد. به Web و فایل‌های بزرگ Infrastructure منطق جدید اضافه نکن.
  فایل‌ها و کلاس‌ها کوچک و تک‌مسئولیتی.
- کامنت فارسی برای کلاس، متد و قواعد مهم؛ نام‌گذاری فنی انگلیسی؛ UI، پیام‌ها و مستندات فارسی.
- زمان‌ها در دیتابیس UTC؛ نمایش جلالی و Asia/Tehran؛ دقت برنامه‌ریزی یک ساعت.
- هیچ‌چیز را «انجام‌شده» اعلام نکن مگر با شاهد: `dotnet build`، `dotnet test` و وضعیت CI.
  اگر نمی‌توانی اجرا کنی بگو «اجرا نشد» و دستورش را بنویس.
- مخزن عمومی است: هرگز رمز، اطلاعات اتصال SQL/AD/پیامک، فایل پشتیبان یا داده واقعی سازمان را
  در کد، تنظیمات، آزمون‌ها یا مستندات نگذار.
- آنچه فقط در محیط واقعی تست می‌شود را صریحاً «تأییدنشده» گزارش کن.
- از معماری، نام‌گذاری و فناوری‌های تعیین‌شده تخطی نکن. چیزی را که در فایل‌ها یا کد نیست حدس نزن؛
  اگر اطلاعات کم است بپرس.
- اگر تصمیم تازه‌ای گرفته شد، به‌روزرسانی `SPEC.md` یا `BACKLOG.md` را پیشنهاد بده.
- خروجی کوتاه باشد: diff یا فقط فایل‌های تغییرکرده، نه کل فایل‌های بزرگ.

## پایان چت (برای جلوگیری از پر شدن چت)

بعد از اتمام هر ۳ آیتم، یا وقتی چت طولانی شده (پاسخ‌ها کند یا ناقص شدند)، یا در شرایط توقف،
کار را با این بلوک تمام کن و ادامه نده:

```
🔚 پایان این چت — لطفاً چت جدید باز کنید
- انجام‌شده (با شماره PR و وضعیت CI):
- نیمه‌کاره:
- تصمیم‌های تازه:
- موارد نیازمند تصمیم یا بازبینی مالک:
- کار بعدی:
- پیام شروع برای چت بعدی (آماده برای کپی):
  «docs/development/AI-WORKFLOW.md را از شاخه develop بخوان و اجرا کن؛
  آخرین وضعیت را از BACKLOG.md و کامیت‌های develop بگیر.»
```

اکنون مرحله ۰ تا ۳ را اجرا کن.
