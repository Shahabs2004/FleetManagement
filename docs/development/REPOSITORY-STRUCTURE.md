ساختار دقیق پروژه‌ها و تعداد فایل‌ها در زمان ایجاد Solution نهایی می‌شود. هر ماژول می‌تواند پروژه‌های Domain و Application و Infrastructure مستقل داشته باشد؛ این تفکیک باید با مرز واقعی ماژول و نیاز توسعه متناسب باشد و به ایجاد پروژه‌های بی‌دلیل منجر نشود.

## قواعد کدنویسی

- هر کلاس فقط یک مسئولیت اصلی داشته باشد.
- فایل‌ها کوچک، خوانا و دارای نام معنادار باشند.
- از کلاس‌های چندمنظوره و فایل‌های بسیار طولانی پرهیز شود.
- کامنت‌ها و مستندات درون کد به زبان فارسی نوشته شوند.
- نام کلاس‌ها، متدها، خواص و متغیرها از قراردادهای استاندارد C# پیروی کنند.
- کامنت باید چرایی تصمیم یا قاعده غیر بدیهی را توضیح دهد، نه اینکه صرفاً همان خط کد را تکرار کند.
- اعتبارسنجی ورودی در مرز مناسب انجام شود و قواعد دامنه دور زده نشوند.
- عملیات چندمرحله‌ای حساس با تراکنش و کنترل هم‌زمانی مناسب پیاده‌سازی شوند.
- زمان‌ها، اعداد و شناسه‌ها در ذخیره‌سازی با قالب استاندارد نگهداری شوند؛ تبدیل به ارقام فارسی فقط در نمایش انجام شود.

## نسخه‌بندی Git

- `main`: نسخه‌های پایدار
- `develop`: شاخه یکپارچه‌سازی توسعه
- `feature/<name>`: قابلیت‌های مستقل
- `fix/<name>`: اصلاح خطا
- Commitها کوچک و با پیام روشن باشند.
- تغییرات بزرگ از طریق Pull Request قابل بازبینی باشند.

## کیفیت

- برای قواعد دامنه، Unit Test نوشته شود.
- برای دسترسی SQL و سرویس‌های بیرونی Integration Test تعریف شود.
- برای مرزهای لایه‌ها Architecture Test در نظر گرفته شود.
- Build و Test باید در CI اجرا شوند؛ موفقیت آن‌ها فقط پس از اجرای واقعی اعلام شود.
